# Repoctopus workflow

Work from the Workspace containing `repoctopus.yaml`. Use the installed `repoctopus` CLI (`repoctopus.cmd` in Windows PowerShell). Use `--workspace <workspace>` and `--json` for the workflow commands below.

1. Establish intent and identity. For an explicit new Change, obtain the Change ID and target branch, then run `repoctopus run start --change <change-id> --target <branch>`. For an existing Change, obtain its Run ID and run `repoctopus run resume --run <run-id>`. Ask for missing or ambiguous inputs before acting.
2. Follow the current Runtime response. Keep the same Workspace and Run ID. Use `run status` to inspect and `run next` to let Runtime advance pending outcomes or dispatch Runtime-owned work. Use the structured continuation and current Work, including its attempt and capabilities. Consult the returned `nextActions` for Runtime-owned Verify and Archive commands.
3. When Runtime offers executable agent Work, use `run work-claim --run <run-id> --adapter manual --attempt <attempt> --runner <runner> --host-capabilities <actual-capabilities>`. Read `result.entryRunner` and `result.changeLifecycle.currentWork.capabilities` from `run status`. Pass supported capabilities as one comma-separated argument. For a new unclaimed Work with a null attempt, use `1`. On retry, use the Runtime continuation for that Work and the next authorized attempt. `entryRunner` is the stable identity of this Workspace, Run and local caller. Preserve an established compatible Runner and its available capabilities across commands. If an existing binding differs, follow Runtime recovery using your own identity. Declare only capabilities you can actually provide. If your native loader can prove the exact project path and bytes it loaded, or your command output requires reading individual layers through the checked loader in step 4, add `--skill-reference-host <host>` with your current host ID: `codex`, `opencode`, `codebuddy`, `codearts`, `trae` or `trae-cn`. This option changes delivery only.
4. Save the full claim JSON to a local temporary file if the Host limits command output. Parse that response, then read it in sections as needed. Do not claim again just to recover truncated output. Execute only when the claim returns `executionAcquired: true`. Read the returned `result.packet.context.layers` in order, including the Action Skill's real body and its attached resources. For a layer with `reference`, use its zero-based index to run `repoctopus run work-content --run <run-id> --runner <runner> --invocation-id <invocation-id> --host-id <host-id> --packet-digest <packet-digest> --skill-reference-host <host> --layer-index <index>`. Read the returned layer body and resources. This command verifies the bytes it actually returns, or supplies the original packet layer if the local files changed. Keep the claim's layer order and digest. A host that can itself prove the exact project path and bytes it loaded may use its native loader. A name-only Skill invocation does not establish that proof. For older packets, read verified `result.recoveredSkillResources` by layer index and digest when present. Use resource paths relative to their Skill, interpret the declared encoding, and read the relevant resources before reporting consumption. A name, path or digest alone is not loaded content. Load only the content bound to the current Action. Execute resource scripts only with the applicable permissions. Follow the packet's output contract and use the same invocation, Host and packet identities to submit the Outcome. Return only actual consumed Skill layer digests via `run work-outcome --consumed-layers`, and use a stable submission ID when retrying the same submission.
5. For a human decision, read `run decision --run <run-id>`, show its real choices through the Host or conversation, and return the user's decision via `run decide --response-file <file>`. Wait for the answer. For wait, reconcile, correction, or re-observation, retain the current Run and use its recovery instructions; do not re-execute an unacquired Action. Stop when Runtime reports done or hands control back to the user.

Report missing or unavailable content before executing. Runtime owns the lifecycle, approvals, scopes, and validation. The Workspace guide at `docs/repoctopus/workspace-guide.md` covers the CLI and team setup.
