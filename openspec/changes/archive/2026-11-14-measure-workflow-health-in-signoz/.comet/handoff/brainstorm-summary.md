# 候选设计

## 统计事实

- 从现有 Trajectory 的 `run.started`、已接受的 `design.approved` 及生命周期事件投影。先核对批准时冻结的 BuildStrategy，再发布执行、测试与隔离枚举；配置分布取截止时最后一份有效批准。阶段、状态和原因以同一次持久化更新为准，原因映射为固定类别，未知保留为未知。重复读取、CLI 进程启动和重复回执不构成变化。
- 同一 Run 使用 Workspace 与 Run 的稳定身份，事件按原 event ID 去重和按 Trajectory sequence 排序。控制台重启、同阶段重试和乱序重放不改变回退数。回退判定来自实际转换的前后阶段与状态机顺序。
- 在现有完成终态日志内带上从完整 Trajectory 复算的跨阶段回退总数及六条路径计数。看板按终态时间选择完成集合；零回退显式记录为零，历史终态缺少有效汇总时显示覆盖缺口。窗口前的回退即使已超出 SigNoz 日志保留期，也能计入本次完成。原转换事件保留用于明细排查。

## 投递

- 本地接收器仍按现有标准 OTLP 即时消费。远端默认保留四项面板所需的小集合及关键诊断；诊断模式可沿用完整信号。信号选择只发生在投递边界，共用规范 envelope 和允许列表，不按目的地重新判定领域状态。
- 复用有限容量的 outbox。短生命周期应用在请求关闭前统一执行有界远端 flush，合并该请求产生的多次写入；达到记录、字节或等待预算时分批处理。无需守护进程，关闭中断后的待投递批次由下一次正常调用恢复。
- 每个目的地的每个信号持久化独立确认位置。对同一 Workspace 的状态提交复用进程间可恢复锁及重新读取，确保并发 CLI 不覆盖彼此的追加或确认。网络等待保持在数据写入锁之外，同一目的地与信号的并发回放需要避免重复领取。旧目的地游标按已确认的既有语义恢复；解释不清的数据标出覆盖缺口。
- 对明确拒绝、确认未知、OTLP 部分拒收分别记录。OTLP 只返回部分拒收计数，不提供被拒记录身份，原批次不作为完整成功；也不自动整批重发已可能接收的记录。使用可定位的有界缺口说明与后续恢复策略。Metrics 继续使用有界维度，四项准确计数以可去重日志为准。

## 查询和验收

- 使用可导入的 SigNoz 看板和 ClickHouse 日志查询，按开始或终态窗口选取 cohort，面板时间上界用于恢复状态。未到终态按截止时间保留当前 phase、status、原因与进入时间。分母为空显示无样本，旧版本或保留期导致观测不全时标示覆盖范围。
- 已在本地 SigNoz 0.150.0 的 Query Range API 验证跨窗口、去重和零回退样本。SQL 夹具使用 2 个完成 Run、1 条窗口前回退和 1 条重复记录，实际结果为 2、1、0.5。该验证只证明查询能力。正式 Verify 使用实际安装包、多仓工作流和本地 MCP 执行真实入库、导入、回读及对账。
- TDD 覆盖多进程、信号分裂、过滤合批、审批失效、暂停恢复、未知和窗口边界。验收使用稳定标记隔离前后端样本，分别统计请求、入库与重复记录，确认桌面在远端失败时仍能实时更新。

不需要 Spec Patch。技术实现细化沿用已批准的四项口径和八项任务。
