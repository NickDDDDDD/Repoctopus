## Context

当前 Windows 桌面已有独立的 OTLP Receiver、版本化只读 IPC 和按 Workspace、Change、Run 关联的投影。现有管理执行在宿主提交 Outcome 后记录 `delegation.completed`，没有可以证明子 Agent 正在工作的事实。此次以确认过的多 Run 原型为界面基线，并补齐这个观测缺口。

## Goals / Non-Goals

在首屏同时监看多个 Run，看到谁在处理、何时需要干预，并能放大一个 Run 查看所有已知事实。沿用宿主审批和桌面现有接收、重放及窗口生命周期。范围限于本地工作台与支撑它的受管委派观测。

## Decisions

1. 每条卡片绑定完整 Run 身份。列表保持可滚动，局部更新不重新选择 Run。点击展开进入同窗口详情，收起时恢复滚动位置与焦点。首屏按 1、2、3、4 列密度排列，再按窗口宽度降列。放大后的子 Agent 独立换行。
2. 复用现有下一步判定。当前有效的人工决定采用琥珀色和明确文案，继续由 Agent 会话展示材料和收集选择。执行、外部等待、阻塞、终态和观测异常使用各自的文字及视觉标识。
3. Runtime 将 Host 实际观察到的活动验证后写入同一个 Trajectory 和标准 OTLP 流。只包含有界的角色、父子身份、任务及仓库标识和已证实的里程碑。现有完成回执继续作为执行结果的依据。没有经过验证的活动、工作范围或进展保持未知。
4. 投影只把属于当前有效 Work 且观测可信的子执行计入活跃总数。重复、迟到、父 Work 替换、终止与冷恢复使用现有顺序和快照机制。继续保留完整运行诊断。

## Risks / Trade-offs

实时视图的精度取决于宿主能实际观测到的活动。通过工作边界事件与三种可重复验证的情况控制误报：真实运行、只有完成回执、与父工作失联。正式 Design 需明确宿主提交入口、幂等身份、哪些字段可进桌面投影和远端降噪策略。
