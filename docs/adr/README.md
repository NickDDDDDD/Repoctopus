# 架构决策记录

本页定义 Repoctopus 何时把设计决定保留在 OpenSpec `design.md`，何时由 Agent 与用户共同确认后创建架构决策记录（ADR）。默认位置始终是当前 change 的 Design；ADR 只保存跨 change 的长期决定。

## 选择记录位置

先按决定的作用域选择唯一记录位置，避免同一结论出现多个权威版本。

| 内容                                           | 记录位置                              |
| ---------------------------------------------- | ------------------------------------- |
| 当前 change 内可回退的设计决定、实施约束或偏差 | `openspec/changes/<change>/design.md` |
| 产品行为和验收标准                             | 对应 Delta Spec                       |
| 工作拆分和完成状态                             | `tasks.md`                            |
| 测试过程、结果和恢复事实                       | Repoctopus Evidence 与正式验证报告    |
| 跨 change 的长期架构决定                       | 经确认的 `docs/adr/<date>-<slug>.md`  |

不要创建共享实施日志、第五份 OpenSpec 产物或把测试输出放进 ADR。

## 识别 ADR 候选

Agent 使用以下信号筛选候选，而不是自动批准 ADR。任一高风险信号成立，或其余信号中至少三项成立时，Agent 应向用户提出 ADR 候选。

| 信号         | 判断问题                                                 |
| ------------ | -------------------------------------------------------- |
| 跨 change    | 这个决定是否会约束多个后续 change、组件或团队？          |
| 长期有效     | 当前 change 归档后，维护者是否仍需理解这项决定？         |
| 难以回退     | 改变决定是否需要数据迁移、协议升级或跨团队协调？         |
| 多种可行方案 | 是否存在多个合理方案，未来维护者需要知道取舍理由？       |
| 高风险       | 是否影响公共契约、持久数据、安全、隐私、合规或信任边界？ |

高风险信号不使用数量阈值。只要它成立，Agent 就必须提出候选并暂停受影响的设计决定；不受影响的工作可以继续。

## 共同确认决定

ADR 创建遵循一个明确的人机确认边界。

1. Agent 先说明决定标题、触发信号、备选方案、推荐方案和错误决定的后果。
2. 用户确认“创建 ADR”或决定仍留在当前 `design.md`。
3. 用户确认后，Agent 创建状态为 `Accepted` 的 ADR，并从相关 `design.md` 链接它。
4. 用户未确认时，Agent 不把评分、实现现状或自己的推荐解释为批准。

如果工作可以安全采用可回退默认值，Agent 把该决定留在 Design 并继续。如果候选涉及高风险或决定会改变已批准范围，Agent 必须把受影响工作作为 Human Decision 暂停。

## 命名和并发规则

每份 ADR 只记录一个决定，文件名使用 `YYYYMMDD-short-kebab-slug.md`。并行分支出现同日同名时，在 slug 后追加 change ID；不要为了分配连续编号而修改共享索引文件。

ADR 状态使用 `Proposed`、`Accepted`、`Superseded` 或 `Deprecated`。已接受 ADR 的决定和理由保持不可变；后续改变创建新 ADR，并用相互链接的 `Supersedes` 和 `Superseded by` 字段建立关系。格式见 [ADR 模板](template.md)。
