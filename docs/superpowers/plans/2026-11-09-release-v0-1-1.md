# v0.1.1 版本维护与发布准备实施计划

<!-- comet-task-authority: openspec/changes/release-v0-1-1/tasks.md -->

目标与约束以 proposal、product-distribution delta 及 design.md 为准。当前 Agent 按已批准的 autonomous + TDD + thorough 实施，并完成独立审查。Tasks 是唯一勾选权威，本文件仅映射任务。

## 全局约束与审查重点

- 产品版本取自本产品根包，不能读取消费者 cwd 元数据；保留插件、协议、schema、依赖版本语义。
- 不更改 Runtime 阶段和恢复规则，不替换已公开资产。范围内审批按用户授权代理，冲突及降低验证要求停止。
- 真实安装包和用户输出是验收边界；源码的常量比较不能代替消费验证。
- 留意 CLI/Host 构建入口的 JSON 内联、三个信号的 Scope、Collector 服务名覆盖、新版/旧版候选混用和首次/重复 npx 调用。

## 1.1 包与 CLI 产品版本

<!-- comet-task-ref:26f78004-36cd-4b04-92b3-c3bdb673eb83 -->

新增公开 CLI 版本回归并扩展包 E2E 的版本断言，以根元数据作为期望。更新根包与根 lockfile 自身版本到 0.1.1（不更新依赖），运行实际 CLI 回归证明旧常量输出不匹配。新增 `platform/product/version.ts` 静态导入包元数据，CLI 改用共享值；在 architecture-governance 既有 plugin-composition 所有权下登记新路径。回归、类型检查、构建及品牌扫描通过后提交并立即 push。真实安装包版本稍后在 2.1 集成核对，不提前宣称完成。

## 1.2 产品观测版本

<!-- comet-task-ref:48f85edd-23cd-4d56-8ead-e5498cd7e888 -->

在 `test/observation-telemetry.test.ts` 为 remote/desktop Resource 和服务名覆盖补充包版本断言；在 `test/otlp-envelope-codec.test.ts` 验证 trace/log/metric Scope。运行得到旧 0.1.0 失败，再将 `services/observation-telemetry.ts` 和桌面 codec 接入共享版本。保留所有遥测字段和插件版本；相关遥测/codec 回归及组合身份快照核对后提交并 push。

独立审查后另补现有显式 OTEL service.version 覆盖的保留回归：Resource 按原优先级覆盖，Scope 仍为包版本。默认包版本测试保持执行，不以覆盖测试取代默认候选验收。此边界通过同一 Run 的正式 Design 修订澄清，配置和已有实现保留。

## 1.3 文档与发布消费入口

<!-- comet-task-ref:fb39d9f9-3b21-47d5-a592-4474d09e4d9f -->

更新 README 与 docs/install.md 的当前版本示例，保留旧版历史。测量脚本通过包版本和既有 releaseAssetNames 取得安装器及示例 Scope。npx smoke 在原帮助/JSON 协议之外核对 --version 与目标产品版本；用已保留旧候选验证拒绝版本漂移，再用新候选验证成功。运行发布策略、文档/打包契约和相关检查后提交并 push。

## 2.1 精确 tarball 的独立消费

<!-- comet-task-ref:f19287c7-e367-4339-9a59-6bc74ee47212 -->

在源码、测试和文档最终提交后构建并记录精确候选与内容摘要；生产安装到仓库外独立目录，运行指定候选包 E2E、实际 --version 和 npx smoke。用新的临时多仓 Workspace、隔离 Store 与真实 Windows PTY 执行 project detect/prepare/review，检查 README/AGENTS/本地教程及链接。沿用已有公开 CLI，不伪造 TTY、不导入源码 apply、不改旧实验。保存退出码、候选身份及原始回执；必要的临时观察进程结束后清理。

## 2.2 独立审查和标准完整验证

<!-- comet-task-ref:69069919-0b12-4c75-a531-1b1a821e809f -->

按 requesting-code-review 与当前 thorough 策略完成独立分段和最终集成审查。新报告保存在 `verification/release-v0-1-1/verification-report.md`，绑定实际 tested implementation commit 和实际候选内容摘要；验证报告先冻结提交并 push，再提交 Build。Build Guard 按 check policy 执行精确 `npm.cmd run build`，Verify Guard 执行精确 `npm.cmd run verify`，`VITEST_MAX_WORKERS=2`。不在检查期间提交或修改输入，不以旧 Change 报告代替新候选证据。结果以实际收据为准。

## 交付与发布操作

任务 2.2 的完成表示独立审查、真实消费证据和报告就绪；实际完整 Verify 是随后 Runtime Guard 的阶段动作，通过前不得归档。此处只澄清 Build 任务与阶段检查的顺序，不删除或降低完整验证要求。任务正文按此更新，稳定 ID 保留，通过 revision-bound revise-plan 重新接受任务权威与计划；已有配置和实现继续保留。

此处是 OpenSpec Workflow follow-up 的执行参考，不新增任务勾选。按同一 Run 归档、创建 PR、等待 CI 后 merge（不 squash），再等待精确 main push CI。固定该 SHA/Tag 启动 release.yml prepare，保存 workflow run/attempt/artifact ID；核对成功候选、草稿及 SHA256SUMS 后，以同一 SHA/Tag/artifact ID 启动 publish。等待 public-smoke 并核对公开资产身份，再报告发布完成。已有草稿或未知上传先查事实并复用原候选；不重建覆盖已绑定资产，不在发布后回写归档目录。
